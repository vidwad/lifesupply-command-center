# Staging Environment Guide — Phase 11B

**Document status:** Phase 11B design + procedure document (Ready for Review)
**Controlling plan:** `docs/20_PHASE_11_DEPLOYMENT_READINESS_PLAN.md` §4 (11B)
**Register rows covered:** 11B-01 … 11B-14; blockers BLK-01, BLK-02, BLK-03, BLK-07; decisions DEC-01, DEC-02, DEC-03, DEC-12
**Prepared:** August 4, 2026

This document is the repository-side half of Phase 11B: the environment
design, the repeatable procedures, and the evidence templates. The other
half — actually provisioning Render resources, creating an Inngest staging
environment, and pasting credentials — can only be performed by the product
owner or a delegated technical admin and is listed in §8. **Nothing in this
document has been executed against real infrastructure.**

---

## 1. Design summary

Two fully separate Render blueprints, one per environment:

| Environment | Blueprint file | Services | Database | Tracked branch | Auto-deploy |
|---|---|---|---|---|---|
| Staging | `render.staging.yaml` | `lifesupply-cc-staging-web`, `-worker`, `-audit-retention` | `lifesupply-cc-staging-db` | `release/phase-11-staging` | ON (staging is for iteration) |
| Production | `render.yaml` | `lifesupply-cc-web`, `-worker`, `-audit-retention` | `lifesupply-cc-db` | `main` today; **subject to DEC-12** | ON today — **BLK-01**, see §7 |

Each service carries a plain `DEPLOY_ENV` variable (`staging` /
`production`), surfaced by `/api/health` as `environment`, so an operator
(or the smoke workflow) can always prove which stack answered. Production's
`render.yaml` does not yet set `DEPLOY_ENV`; add it when DEC-12 is
implemented (see §7 diffs) — until then production reports `unknown`,
which is itself distinguishable from `staging`.

### 1.1 Isolation matrix (never shared between environments)

| Item | Staging | Production | Enforced by |
|---|---|---|---|
| PostgreSQL database | `lifesupply-cc-staging-db` | `lifesupply-cc-db` | Separate `fromDatabase` references per blueprint |
| `AUTH_SECRET` | Generated fresh by staging blueprint | Generated by production blueprint | `generateValue: true` in each blueprint — never copied |
| `MASTER_ENCRYPTION_KEY` (vault) | Staging-generated; worker/cron copy the *staging* value | Production-generated | Blueprint + operator discipline (§4 step 6) |
| Inngest environment + keys | Dedicated staging Inngest env | Production Inngest env | Operator creates two Inngest environments (§4 step 7) |
| Object storage bucket | Staging bucket (pending DEC-03) | Production bucket (pending DEC-03) | `S3_*` set per environment, never shared |
| Integration credentials | Sandbox/test only (QBO sandbox, Mailchimp test audience, mock supplier portal) | Real credentials | Vault entries are per-database, so isolation follows the DB split |
| OAuth redirect URIs | Staging URL registered on a *sandbox* Intuit app | Production URL on the production app | Separate app registrations (§8) |
| Email audiences / senders | Test audience + test sender only | Real audiences | DEC-07 + 11D-09 |
| Auth/app URLs | Staging onrender.com URL | Production domain | Per-service `AUTH_URL` / `NEXT_PUBLIC_APP_URL` |

A consequence of vault isolation: because integration credentials live
AES-encrypted in each environment's *database*, splitting the databases
automatically splits every vault credential. There is no shared secret
store to cross-contaminate.

## 2. Connection matrix — `DATABASE_URL` / `DIRECT_URL` per process (11B-03)

`prisma/schema.prisma` declares both `url = env("DATABASE_URL")` and
`directUrl = env("DIRECT_URL")`.

| Process | How it starts | Uses `DATABASE_URL` | Uses `DIRECT_URL` | Runs migrations? |
|---|---|---|---|---|
| Web (Render) | Dockerfile CMD: `pnpm prisma migrate deploy && pnpm start` | Runtime queries (Prisma Client) | `prisma migrate deploy` at container start | **Yes — the only migrator** |
| Worker (Render) | `dockerCommand: pnpm worker` (overrides CMD) | Runtime queries | Not used (no migrate invocation) | No |
| Cron (Render) | `dockerCommand: pnpm tsx scripts/cron/audit-retention.ts` | Runtime queries | Not used | No |
| CI (GitHub Actions) | `pnpm build` → `prisma generate` | Schema-only placeholder; never connects | Schema-only placeholder (added in Phase 11B — BLK-03) | No |
| Local dev | `pnpm db:migrate` etc. | Local compose DB | Same local DB | Yes (dev migrations) |

Key facts:

- On Render both variables come from the same `fromDatabase.connectionString`
  — a **direct** connection (Render Postgres has no built-in pooler in this
  setup). That is correct: `directUrl` exists so migrations bypass any
  pooler. **If a pooled URL (e.g. PgBouncer) is ever introduced, only
  `DATABASE_URL` may point at the pooler; `DIRECT_URL` must stay direct or
  `migrate deploy` can deadlock.**
- Only the web service migrates. Worker and cron override the Dockerfile CMD
  precisely so that concurrent containers never race on migration locks.
- **BLK-03 resolution:** `.github/workflows/ci.yml` now sets a schema-only
  `DIRECT_URL` alongside the existing schema-only `DATABASE_URL`, so a
  future CI step running `prisma validate` or `prisma migrate` cannot fail
  with `P1012: Environment variable not found: DIRECT_URL`. CI still never
  opens a database connection.

## 4. Staging provisioning runbook (11B-01, 11B-02, 11B-06, 11B-10)

Repeatable from this repository alone. Prerequisites: DEC-01 (Render
confirmed), DEC-02 (database plan), and a Render account owner.

1. **Cut the staging release branch** from the accepted baseline:
   `git checkout -b release/phase-11-staging <baseline-sha> && git push -u origin release/phase-11-staging`.
   (Convention: `docs/RELEASE_READINESS_STATUS.md` §4.1. Tag `v0.9.0-staging`
   from this branch once the first staging deploy passes the smoke test.)
2. **Apply the staging blueprint**: Render dashboard → Blueprints → New →
   point at this repo, blueprint file `render.staging.yaml`, branch
   `release/phase-11-staging`. Render creates the database + three services.
3. **Wait for the first web deploy.** The Dockerfile CMD runs
   `prisma migrate deploy` — on the fresh staging DB this must apply **all
   21 migrations** (count at baseline). Capture the deploy log as evidence
   for 11B-05 / GATE-01.
4. **Set `AUTH_URL` and `NEXT_PUBLIC_APP_URL`** on staging web to the URL
   Render assigned, then redeploy.
5. **Create the staging Inngest environment** at app.inngest.com (separate
   environment or app from production). Copy its event key to staging web +
   worker and its signing key to the staging worker.
6. **Copy the staging `MASTER_ENCRYPTION_KEY`** (generated on staging web at
   first apply) to the staging worker and cron services.
7. **Verify worker registration**: the staging Inngest dashboard must show
   the app with all registered functions (BigCommerce syncs, Mailchimp, QBO,
   GA4, supplier check, delay sweep) after the worker boots.
8. **Seed staging** (11B-06): run `pnpm db:seed` **only if** the seed content
   has been reviewed as synthetic. Policy: staging contains no real customer
   data; approved staging users only; all feature flags default OFF (absent
   rows are OFF by design). Record the seeded account inventory.
9. **Run the smoke test** (§5) and file the results.
10. **Clean-room criterion** (11B-10): a second operator, using only this
    document, must be able to repeat steps 1–9 without asking questions.
    Record who performed the rebuild and when.

Decommission/rebuild: delete the staging blueprint resources in Render and
repeat from step 2 — nothing about staging lives outside Render + this repo.

## 5. Staging smoke-test checklist (11B-07, 11B-11, 11B-12, 11B-13)

Two layers: the credential-free CI workflow, then operator checks.

### 5.1 Automated — `.github/workflows/staging-smoke.yml`

Run **Staging smoke test** from the Actions tab with the staging base URL.
It fails unless: `/api/health` responds `ok`/`degraded`; the body's
`environment` is exactly `staging`; the `database` check is `ok`; no
high-risk feature flag is reported ON; and no secret-shaped string appears
in the body. A passing run is the 11B-07 evidence.

### 5.2 Expected `/api/health` body (11B-12)

```json
{
  "status": "ok",
  "environment": "staging",
  "timestamp": "…",
  "uptimeSeconds": 123,
  "checks": [
    { "name": "database", "status": "ok" },
    { "name": "anthropic", "status": "ok" },
    { "name": "feature_flags", "status": "ok", "detail": "no high-risk flags on" }
  ]
}
```

Review conclusion (code inspection, this PR): the endpoint exposes status
enums, a timestamp, uptime, the environment label, and flag *posture* — no
secrets, no row counts, no connection strings, no user data. Error paths
expose only `Error.name`, never messages that could carry a DSN.

### 5.3 Operator checks (authenticated)

| # | Check | Pass condition |
|---|---|---|
| 1 | Log in with a seeded staging admin | Dashboard renders; no real customer data visible |
| 2 | `/admin/feature-flags` | Every high-risk flag OFF |
| 3 | Permission probe: open `/financials` as a role without `financials.view_summary` | Access denied |
| 4 | Staging Inngest dashboard | Worker app registered, all functions listed |
| 5 | **Terminal-state job (11B-13):** trigger a BigCommerce sync with *no credentials configured* — or run "Run delay sweep now" on `/operations` | The run/sync log leaves `running` and reaches a terminal state (`failed` with a clear credential error is a PASS for this check — the point is no stalled `running` row) |
| 6 | `/admin/audit-logs` | The actions from checks 2–5 appear |
| 7 | Cron: Render → staging cron → "Trigger run" | Exit 0; audit-retention line in logs |
| 8 | `/api/auth/quickbooks/connect` without credentials configured | Clean error/redirect, no crash |

Record date, operator, and per-row outcomes in the register's evidence
locations.

## 6. Migration rehearsal and rollback procedure (11B-05, 11B-08, 11B-14, GATE-01)

### 6.1 How migrations run

Only the web container migrates: Dockerfile CMD is
`pnpm prisma migrate deploy && pnpm start`. `migrate deploy` is strictly
forward-only and idempotent — it applies committed, not-yet-applied
migrations in order and no-ops otherwise. Worker and cron never migrate.
**Prisma has no automatic down-migrations**: rollback of a bad migration is
restore-from-backup or a forward fix, never an automatic reversal.

### 6.2 Rehearsal procedure (run in staging before any production migration)

1. **Fresh-database rehearsal (first time / after squashing):** provision or
   reset the staging DB, deploy, and confirm the deploy log shows every
   migration applied (21 at baseline) with zero errors. Record the count and
   log excerpt.
2. **Delta rehearsal (every release):** with staging on the previous
   release, deploy the new release branch and record which new migrations
   applied, their duration, and any lock warnings.
3. **Post-migration verification:** run smoke §5, then spot-check the tables
   the migration touched.
4. **Record the rehearsal** in the register (11B-14) and the runbook drill
   log: date, release, migrations applied, duration, outcome.

A migration that fails in rehearsal blocks the release until fixed —
that is GATE-01.

### 6.3 Rollback procedure (extends `docs/OPS_RUNBOOK.md` §7)

Before every production deploy: confirm the provider backup/PITR point is
current (DEC-02 sets the capability), and know the previous deploy ID.

| Failure mode | Action |
|---|---|
| App bug, schema unchanged | Render → service → previous deploy → **Rollback**. DB untouched. |
| App bug, migration applied but backward-compatible (additive) | Roll back the app image only; leave the schema. Verify with §5 smoke. Plan a forward fix. |
| Migration itself failed mid-deploy | The CMD chain means Next never started — traffic still on the old build. Fix forward (preferred) or restore the DB to the pre-deploy point, then redeploy the previous build. |
| Migration succeeded but is wrong/destructive | **Trip the kill-switch** (runbook §2), restore the DB from backup/PITR to the pre-deploy point, roll the app back, then re-point traffic. Accept data loss back to the restore point — this is why destructive migrations require a pre-deploy backup and expand-contract design (runbook §5). |

Approval gate (11B-08): a production deploy requires (1) CI green on the
release branch, (2) staging rehearsal recorded per §6.2, (3) smoke test
passed on staging, (4) product-owner or technical-lead written approval on
the release PR. The rollback rehearsal — actually performing an app-only
rollback and a DB restore in staging — is executed once staging exists and
recorded in the runbook drill log (feeds GATE-06).

## 7. Stopping automatic production deploys (11B-09, BLK-01 — pending DEC-12)

Today every merge to `main` auto-deploys all three production services.
Two candidate resolutions; **DEC-12 chooses**. Both diffs below are exact;
apply to `render.yaml` for each of the three services and sync the
blueprint. *Not applied in this phase* — recorded as a dependency on
DEC-12, per the register's rule against assuming undecided answers.

**Option A — keep `main`, disable auto-deploy (smallest change):**

```yaml
    branch: main
    autoDeploy: false   # was: true
```

Deploys then happen only when an operator clicks "Deploy latest commit"
(or via API). Simple; the deploy gate is human. Risk: nothing stops an
operator deploying an unreviewed `main` state — the §6.3 approval gate is
procedural, not mechanical.

**Option B — release-branch promotion (stronger, matches the register §4.1
convention):**

```yaml
    branch: release/phase-11-production   # was: main
    autoDeploy: true
```

Production deploys only when a commit is pushed to
`release/phase-11-production`, which per convention is cut only after the
§6 launch gates are Accepted. Merging to `main` becomes deploy-inert.
Recommended: **Option B**, because the mechanical gate matches the
already-documented branch convention — but this is DEC-12's call.

Either option should be applied together with adding
`DEPLOY_ENV=production` to the three production services so `/api/health`
identifies production explicitly.

## 8. Owner-only manual steps (cannot be performed from this repository)

Render: apply `render.staging.yaml` as a new blueprint; set the manual env
vars (§3); copy the staging master key to worker + cron; set the staging
URLs; later, apply the DEC-12 diff to production and sync.
Inngest: create the dedicated staging environment; copy its two keys.
Database: confirm the staging DB plan (DEC-02); no action beyond blueprint.
Storage: decide DEC-03, create separate staging/production buckets, set
`S3_*` values.
OAuth: register a staging redirect URI on a sandbox Intuit app (DEC-06);
create GA4 service-account access and a Mailchimp test audience (DEC-07).
Git: cut `release/phase-11-staging` from the accepted baseline; tag
`v0.9.0-staging` after the first passing smoke test.
Decisions: record DEC-01, DEC-02, DEC-03, DEC-12 in the register.
